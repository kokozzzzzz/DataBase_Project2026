# B-FORMAL-v1 固定测试数据

该测试集使用真实 A/B/D 表结构和服务。所有用户、车辆、地址、渠道凭证均为虚构；D 的密文字段放入明确的测试标记，不代表真实个人资料或正式加密实现。

## 编号与责任

| 对象 | 识别方式 |
| --- | --- |
| B 运营商、站、桩、枪、车位、费率版本、已完成停运、已关闭离线待办、已驳回变更申请 | 编号 7200001–7200020，运营商名和设备序列号 B-FORMAL-v1-01 至 20 |
| D 供本测试集使用的用户、车辆 | 7200001–7200020，实名 VERIFIED、状态 ACTIVE，余额 100.00，车辆属于同号用户 |
| D 测试活动 | promotion_id=7200000，固定减 2 元、20 次发放总量、每用户一张、20 个指定测试站 |
| D 测试券 | coupon_code=B-FORMAL-v1-01 至 20，实际 coupon_id 使用本机自增；20 张均由正式流程核销 |
| A 历史预约 | 7200001–7200020 对应 11 月 10 日，7200101–7200120 对应 11 月 11 日 |
| B 订单、读数、分段、支付和退款 | 由正式服务生成，订单号以本机 manifest 或 admission_id 查出；支付退款均用 B-FORMAL-v1 前缀 |

这些编号为本次 B 测试数据选择。首次执行会检查固定编号，发生占用时整笔回滚并报错。D 原有核心测试账号与 A 9000 段夹具可保留，本程序不修改它们。

## 数据规模

空的 B 结构加载后得到以下行数。已有其他业务样例的数据库，其全表行数会更多。

| 表 | 本测试集行数 |
| --- | --- |
| operator / station / charging_pile / parking_space / charging_gun | 各 20 |
| equipment_status_log | 40 |
| equipment_outage_plan / equipment_change_request / equipment_offline_task | 各 20 |
| tariff_rule / tariff_band | 20 / 60 |
| charging_order / meter_reading / order_fee_detail | 40 / 120 / 80 |
| payment_record / refund_record | 100 / 20 |

另外写入 D 的 20 个测试用户、20 辆车、1 个活动、20 条适用场站、20 张券及20条核销；A 的 40 条历史预约、到站记录与已释放占位及相应状态历史。

每单 07:30 起充，08:00 边界累计 6 kWh，08:30 累计16 kWh。谷电价 0.40、平电价 0.70，服务费 0.20 元/kWh，得到电费 9.40、服务费 3.20、原价 12.60。第一天每单减2元，分6.00与4.60元成功支付，次月退款3元；第二天不减免，先失败1元，之后6.00与6.60元成功支付。

## 安装、重复与回滚

```powershell
python -m app.seed_b_integration
python -m app.seed_b_integration --commit --output ../B_本机实测/固定测试集.json
```

第一条默认回滚，用于查看检查结果，第二条明确提交。生成程序复用公共 DB_* 配置，写入同一 charging_platform。首次成功整笔提交，失败整笔回滚。使用 GET_LOCK 串行化本测试集的生成，避免两次并发加载。自增编号可能在预览或失败时产生空号。

重复执行会核对标记、固定主数据规模、40 笔订单金额和核销券状态，再跳过生成。数据已被改动时拒绝自动覆盖；需要重新生成请使用新测试实例或先评估依赖，不能直接删除已经被 A/D 关联的固定数据。所有测试账户的余额用于启动预检，外部支付样例不扣余额。

固定历史预约通过单独的夹具 INSERT 导入，再调用 A 的到站、B 的开单、计费和支付服务。正式预约入口禁止过去时间，线上业务应继续用 A 的 create_reservation；夹具导入不会修改该限制。
