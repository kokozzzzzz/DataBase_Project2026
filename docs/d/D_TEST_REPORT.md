# D 模块测试报告

## 1. 测试范围

本报告覆盖 D 负责的④用户与会员运营、⑤结算与对账，包括：

- 17张业务表的结构、约束、外键、索引和正式测试数据；
- 6个调用者权限视图和2个存储过程；
- 用户、车辆、会员、企业车队、优惠活动和优惠券业务；
- 结算单、结算明细、对账差异、双方确认、普通发票和红字发票业务；
- Python持久层、业务服务、事务边界和回滚一致性；
- 复杂查询执行计划、最小权限、全量恢复和增量恢复前置条件。

本报告不包含尚未实现的 Web 登录接口或真实支付、短信、电子发票平台测试。

## 3. 测试方法

1. 使用 `sql/D/00_verify_d_all.sql` 对结构、数据、对象数量和业务不变量进行只读验收。
2. 使用 `sql/D/05_settlement_explain.sql` 对5条复杂查询执行 `EXPLAIN ANALYZE`。
3. 使用 `pytest` 对持久层和服务层进行隔离单元测试。
4. 使用7个真实数据库演示入口验证事务内业务结果，并在同一连接中统一回滚。
5. 使用角色、恢复和binlog预检脚本验证安全与运维方案。

测试数据均为虚构数据。D的17张表每表至少20行，满足任务书的数据量要求。

## 5. 复杂查询与执行计划

执行命令：

```powershell
.\.venv\Scripts\python.exe -m app.run_sql --file sql/D/05_settlement_explain.sql
```

| 查询 | 业务目的 | 主要访问路径 | 结论 |
| --- | --- | --- | --- |
| E01 | 场站账期结算汇总 | `idx_settlement_station_period`、`idx_detail_statement_type_event` | 场站和账期走范围索引；仅对3行聚合结果使用临时表 |
| E02 | 结算单逐订单用户车辆追溯 | `idx_detail_statement_type_event`及各表主键 | 明细按结算单和类型索引定位，关联均为单行索引查找 |
| E03 | 跨期退款追溯原结算 | `idx_detail_order_event`及各表主键 | 按订单定位退款明细，再沿外键主键追溯原明细和结算单 |
| E04 | 双方确认的待调整差异 | `idx_difference_statement_status_time`、`idx_confirmation_difference_party_id` | 差异状态和双方确认均命中复合索引 |
| E05 | 普通票和红字票追溯 | `idx_invoice_settlement_status_time`、`idx_invoice_original` | 结算单发票和原票引用均使用索引 |

测试数据量较小时优化器成本和耗时仅作功能性参考。本次没有出现对业务大表的不必要全表扫描；E01 的 `Table scan on <temporary>` 是小规模聚合临时结果，不是基表扫描。

## 9. 测试中发现并修正的问题

1. 结算退款账期可能为负，原非负约束无法表达真实跨期冲减；已改为允许有方向的应结净额，同时保持事实金额非负。
2. MySQL 8.0.46没有 `information_schema.ROUTINE_PRIVILEGES`；角色验收改为读取 `mysql.procs_priv`。
3. Windows桌面被重定向到D盘，固定使用用户目录会导致备份路径不存在；备份步骤改为先验证实际目录且禁止覆盖。
4. 管理员连接原先继承 `SYSTEM` 时区；最终预检脚本显式设置会话时区为 `+08:00`。
5. 多支付和多退款直接连接会形成乘积并重复汇总；查询和视图先分别聚合支付与退款，再连接订单。

## 10. 已知限制

- 统一终端用户登录和员工账号系统尚未实施，当前完成的是安全策略与数据库RBAC。
- GTID为`OFF`，本地时间点恢复按binlog文件位置或时间范围执行。
- 支付、退款、短信和电子发票均使用虚构测试记录，没有调用外部生产平台。
- 正式分成比例、合同参数和已发券规则快照仍需由业务方确认。
- 20～60行测试数据可验证正确性和索引路径，不能替代生产数据规模下的压力测试。

## 11. 测试结论

D模块的结构、数据量、复杂查询、持久层、事务一致性、安全权限、备份恢复和关键业务闭环均通过当前课程设计验收。未发现阻塞提交的结构错误、数据残留或核心业务失败；已知限制均已记录，不影响④⑤课程设计功能展示。
