# C 模块③⑦实施与验收说明

## 1. 范围和交付

依据《四人四天任务分工计划》，C 负责：

- **③设备监控与故障工单**：采集运行数据、生成并查询告警、重复派单、接单/到场/修复/复核、设备恢复。
- **⑦备件库存与领用管理**：备件和仓库档案、分仓库存、收货/领用/安装/退料/盘点调整、库存流水和冲正。

新增材料均位于 `yX/`：数据库脚本在 `sql/C/`，PyMySQL 持久层在 `c_app/`，测试在 `tests/`。业务图和原始逻辑字典继续使用 `37E-R图.png`、`C_03_07_data_dictionary.xlsx`。

## 2. 数据模型与跨模块边界

保持原字典的 8 个核心实体：`device_telemetry`、`alarm`、`maintenance_work_order`、`spare_part`、`warehouse`、`inventory`、`inventory_transaction`、`work_order_part`。

- 本模块内部主键统一 `BIGINT UNSIGNED`，金额/测量值使用定点 `DECIMAL`，时间统一到 `DATETIME(6)`，连接会话使用北京时间 `+08:00`。
- B 维护 `charging_pile`、`charging_gun`、`equipment_status_log`、`equipment_offline_task` 和 `equipment_outage_plan`。C 不复制这些表；设备编号仍按接口清单作为逻辑引用，触发器及过程校验桩/枪是否存在、枪是否属于对应桩。
- DDL 依赖 B 的设施表已经建立。采样故障时，C 将桩/枪状态更新为 `FAULT`，由 B 自己的触发器记录状态历史；达到调用方传入的离线阈值时，C 在 B 的 `equipment_offline_task` 建立待办并更新桩为 `OFFLINE`。
- 维修人员、操作人员 ID 保持不透明外部编号，不另建重复人员主数据表；接入统一账号/人员实体后再由组内确认物理外键。
- 同一告警允许关联多张维修工单，所有工单独立保留。一个维修工单失败复核后可返回 `REPAIR_REQUIRED`，重新维修并复核。

## 3. 库存一致性和事务设计

1. 收货、领用、退料、盘点调整和冲正均由存储过程作为单次原子操作；过程内部锁定 `inventory` 行，核对可用数量，更新 `quantity/version_no` 并追加 `inventory_transaction`，任何一步失败均回滚。
2. 库存更新使用 `SELECT ... FOR UPDATE` 串行化同一仓库/备件写入，并以 `version_no` 条件更新作为额外并发校验。两张工单争抢最后一件备件时，最多一笔领用成功。
3. 领用和退料同时更新 `work_order_part` 与库存流水；账本禁止 UPDATE/DELETE，错误通过反向数量变动的 `REVERSAL` 流水更正。工单库存冲正仅允许在工单处于 `ARRIVED`、`REPAIR_REQUIRED` 或 `REPAIRED` 时执行，已关闭/取消工单不得再改写备件结算。
4. 课程组确认的工单退料规则为**不允许无记录损耗**：工单关闭前，每个备件明细必须满足 `issued_qty = installed_qty + returned_qty`。已安装数量和退回数量不能大于领用数量。
5. 所有 `sp_c_*` 写过程都自行开始、提交或回滚事务，调用时不要再套用外层事务。Python 连接需将这些过程调用视为已提交的独立业务操作；不要把它们和其他模块的写操作组合成跨过程事务。

## 4. SQL 文件执行顺序

从仓库根目录连接已创建的 `charging_platform`，先完成 D、B 模块表结构，再执行：

```sql
SOURCE yX/sql/C/01_schema.sql;
SOURCE yX/sql/C/02_triggers.sql;
SOURCE yX/sql/C/03_procedures.sql;
SOURCE yX/sql/C/04_views.sql;

-- 仅在 C 表为空、且 B 至少有一条桩和一把属于该桩的枪时执行。
SOURCE yX/sql/C/05_seed.sql;
-- 检查八张表的行数均达到要求后，人工执行 COMMIT；有误则 ROLLBACK。

SOURCE yX/sql/C/07_verify.sql;
SOURCE yX/sql/C/06_business_queries.sql;
SOURCE yX/sql/C/08_constraint_tests.sql;
```

DDL 会隐式提交，不能依赖一个事务回滚整批建表。首次执行前确认 C 的八张表、八个触发器、十二个过程及六个视图不存在；不要用清库、DROP 业务表或 TRUNCATE 方式重跑。数据种子故意不自动提交。

`05_seed.sql` 使用 B 数据库中当前已有的第一条桩和其一把枪做测试引用，不伪造 B 主数据。若 B 尚无测试设备，先由 B 准备设施测试数据。种子脚本为每张 C 表各追加 20 条虚构数据；清空前不要重跑，以免混入额外样例。

## 5. SQL 对象

### 表和约束

- 8 张表、78 个字段；各表有主键、查询索引和 CHECK 约束。
- 告警、工单使用显式状态机；里程碑时间必须按派单→接单→到场→修复→复核递增。
- `inventory` 对 `(warehouse_id, spare_part_id)` 唯一；数量不能小于已锁数量。
- `inventory_transaction` 外键关联 C 内部仓库、备件、工单和原流水；流水编号唯一，调整值与前后库存必须相符。
- `work_order_part` 对工单、备件、领用仓库组合唯一；限制超领、超装、超退。

### 触发器

`02_triggers.sql` 创建 8 个触发器：校验桩/枪关系和遥测来源、阻止非法告警/工单状态迁移、校验库存流水与当前库存相符、禁止修改或删除库存流水、约束工单备件数量单调性。共享设备状态历史仍由 B 的触发器负责。

### 存储过程

`03_procedures.sql` 创建 12 个过程：

1. `sp_c_ingest_telemetry`：写采样，按故障码创建/复用未解决告警，联动 B 设备状态和可配置离线待办。
2. `sp_c_dispatch_work_order`：针对告警派发新的维修工单并确认告警。
3. `sp_c_advance_work_order`：接单、到场、登记修复结果。
4. `sp_c_verify_work_order`：通过/驳回复核；通过后在没有其他未结告警/工单时恢复设备。
5. `sp_c_cancel_work_order`：仅允许取消尚未接单的工单。
6. `sp_c_plan_work_order_part`：创建工单备件计划。
7. `sp_c_receive_stock`：收货入库和流水。
8. `sp_c_issue_work_order_part`：锁库存、向工单领料并记流水。
9. `sp_c_return_work_order_part`：退回未安装备件并记流水。
10. `sp_c_record_part_installation`：记录实际安装数量。
11. `sp_c_adjust_stock`：有原因的盘点调整。
12. `sp_c_reverse_inventory_transaction`：使用反向流水冲正原交易，并同步更正未消耗的工单数量；领用冲正后会根据新数量重新判定备件明细为计划、领用或完成状态。

### 视图和业务查询

`04_views.sql` 提供六个调用者权限视图：告警看板、工单队列、24 小时设备健康、可用库存、工单备件对账、30 天库存周转。`06_business_queries.sql` 提供六条跨三张及以上关系的运营/审计查询，覆盖告警负载、维修响应、异常遥测、库存充分性、流水和备件消耗。

## 6. Python 持久层与测试

- `c_app/repository.py`：参数化分页查询、遥测写入、告警/工单/库存读取、备件/仓库档案维护和存储过程调用。
- `c_app/service.py`：遥测测量值与告警入口校验、告警派单和看板操作。
- `c_app/run_demo.py`：复用项目 `.env` 和 `app.database.connection`，只读展示告警、工单和库存看板。
- `tests/test_c_repository.py`、`tests/test_c_service.py`：不连接 MySQL 的单元测试，验证参数绑定、分页/状态校验、时间区间、档案写入和输入保护。
- `tests/verify_c_module.py`：只读真实数据库验收，检查对象数量、每表数据量、库存流水对账、无损耗和 B 设备引用；可用 `--output yX/test-results` 保存 JSON。

运行 Python 单元测试：

```powershell
python -m pytest -q yX/tests
```

配置根目录 `.env` 且按顺序建表、种子提交后，运行：

```powershell
python yX/c_app/run_demo.py
python yX/tests/verify_c_module.py
```

如需从数据库导出最终物理字段清单：

```powershell
python yX/tools/generate_c_data_dictionary.py
```

该脚本读取部署后的 `information_schema`，生成 `yX/C_03_07_physical_dictionary.csv`；DDL 和数据字典若有修改，应重新执行导出。

## 7. 安全、权限和备份恢复

- 所有 Python 用户输入均通过 PyMySQL 参数绑定；动态筛选只来自固定状态白名单，过程名称使用白名单，不拼接用户输入。
- C 模块不保存车主手机号、车牌等个人敏感信息；维修人员、操作人员仅存外部 ID。业务库账号应按角色最小授权，不使用应用账号运行 DDL。
- 过程和视图采用 `SQL SECURITY INVOKER`，不会提升调用者权限；需要依据学校 RBAC 要求在实际 MySQL 实例配置只读看板角色、维修人员角色和仓管角色。表格的细粒度列级授权、账号表来源仍需小组统一确定。
- 设备遥测可能高频增长。先依 `ix_telemetry_pile_time`、`ix_telemetry_gun_time` 查询，实际数据量增大后依据 `EXPLAIN ANALYZE` 评估分区/归档，不预先启用会改变历史查询口径的删除任务。
- 备份沿用项目全库策略：由管理员对 `charging_platform` 执行定期全量 `mysqldump --single-transaction --routines --triggers --events`，加密存放、限制访问并保留离线副本；备份中包含个人信息时仍按全组数据分级策略保护。恢复先导入隔离实例，再执行 DDL/行数/库存流水对账和业务验收，确认后切换服务。频率、RPO/RTO 和恢复演练日期须由小组在总报告中确认。

## 8. 验收边界与待全组确认

Python 单元测试当前为 13 项通过；但 SQL 仍需在具备 MySQL 8.0.46、D/B 表及 B 测试设备的实例上实际执行并保存结果。离线判定阈值作为 `sp_c_ingest_telemetry` 参数传入，不把 B 文档里的临时 180 秒值固化为正式规则。停运计划仍是 B 的唯一共享表，登记责任人由 A/B/C 共同确定；C 不另建计划实体。

`yX/tests/verify_c_module.py` 是只读验收脚本，不能替代真实的双连接并发领料演示。并发实测应使用一条库存为 1 的备件、两个独立工单和两个连接，记录一个成功、一个库存不足，并验证库存与流水；执行前需使用专门测试环境，流水不可删除，测试冲正也会留下永久审计记录。
